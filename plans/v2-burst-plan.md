# shinnku-bot v2：一陣問題同時來時怎麼接

寫於 2026-11-14，接在 [v2-gaps-plan.md](v2-gaps-plan.md) 之後。只是計劃，代碼還沒動。

它替換 `harness/engine.py` 裡“一個群只有一個觸發者”的那一套（防抖、取消重來、`dirty`），連帶 `harness/send.py`、`harness/act.py` 的 `say` 工具和 `harness/hooks.py` 的條數截斷。

## 1. 問題

2026-11-14 16:18–16:45（UTC）一個群裡幾個人輪流 @ 和回覆 bot，連著出難題。下面的數字都來自服務日誌，日誌裡只有條數、字數和耗時。

## 2. 結論一覽

| 要決定的 | 決定 | 見 |
|---|---|---|
| 工作單位 | 按問題記賬，按輪調用：每條衝我來的消息單獨記一筆，模型一輪只調一次，一次看完所有還沒回的 | 3.2、3.5 |
| 怎麼記，保證不丟 | 每個群一個內存隊列，問題有明確的狀態；看過不回算處理完，失敗的回到隊列 | 3.2 |
| 生成和發送時進來的消息 | 不取消，排進下一輪 | 3.3 |
| 一次答幾個人，怎麼對上號 | 一次調用答整批；`say` 的每條帶 `to`；只在說不清時，在末尾加一張“還沒回的”清單；`transcript.py` 不動 | 3.4、3.5 |
| 引用 | 單個問題照舊（目標固定）；多個問題時每組第一條都引用 | 3.6 |
| 順序和公平 | 先來後到，每輪最多 6 個、每人最多 3 個，超出的排下一輪 | 3.7 |
| 長回覆和代碼 | 不截斷，超出的行合併；代碼整塊發一條；一輪最多 12 條；不為長度重試 | 3.8 |
| 延遲、超時、過期 | 一輪封頂 60 秒；SDK 不自己重試；問題 5 分鐘過期 | 3.9 |
| 被限流 | 先換另一個模型，再全局退避，問題回到隊列；不說固定的話 | 3.10 |
| 主動發言、停止前 | 問題優先；`drain` 等隊列走完 | 3.11、3.12 |
| 問題分類的接口 | 問題可帶 `profile`，按 `profile` 分批 | 3.13 |

幾條原則：

- **一條都不丟**。沒回的問題都有記錄，最後只能是“回了”“看了不回”“過期”三種結局之一，後兩種也記日誌。
- **調用開始了就不取消**。取消扔掉的是已經付過錢的調用。
- **看過不回也算處理了**。模型看到了某個問題、選擇不回，就跟現在的 `stay_silent` 一樣，不再追。這樣不會因為一條刷屏而一直循環調用。
- **調用次數隨時間增長，不隨問題數增長**。一陣子裡來十個問題和來兩個問題，調用次數差不多。

## 3. 架構

### 3.1 流程

```
收到消息    存庫（和現在一樣）
  衝我來的？    是（私聊、回覆我、@我、叫名字）→ 記成一個問題，狀態 open
              否，發消息的人有 open 的問題 → 他還在打字，延長安靜窗口
              否，發消息的人的問題正在回答 → 記成他的追問（每人最多一條，新的替換舊的）
              否 → 只存（話癆程度大於 0 時交給主動發言）

每個群一個 worker，有 open 的問題就轉起來：
  1. 等      提問的人都安靜 2.5 秒，或最早的 open 問題已經等了 8 秒
  2. 取批    open 問題按先來後到取，每輪最多 6 個、每人最多 3 個 → taken
  3. 拼提示詞  最近 30 條照舊，需要時在末尾加“還沒回的”清單
  4. 調模型   一次，不取消
  5. 發      按問題分組，每組第一條按規則引用它回的那條
  6. 收賬    回到的 answered，看了沒回的 passed；失敗的回到 open，稍後重來；過期的 dropped
  7. 還有 open 的就回到 1；沒有就看主動發言；再沒有，worker 退出
```

“什麼算衝我來”（`attention.py`）不變，只多了一條：回答期間提問人自己補的話算追問。現在這種情況是取消重來一次，同樣多花一次調用，但白扔一次；改成追問後，下一輪模型看得到我的回答和他補的話，沒必要回就不回。

### 3.2 問題和它的狀態

```python
@dataclass
class Ask:
    msg: Msg          # 衝我來的那條，進隊時定下，之後不變
    reason: str       # private / reply / mention / name / followup
    arrived: float    # 進隊時間
    state: str        # 見下表
    tries: int = 0    # 失敗過幾輪
```

| 狀態 | 意思 | 去向 |
|---|---|---|
| open | 等著進下一輪 | 進批 → taken；過期 → dropped |
| taken | 在這一輪的提示詞裡 | 回到了 → answered；看了沒回 → passed；這一輪失敗 → open（tries 加 1） |
| answered、passed | 處理完了，從隊列裡刪掉 | — |
| dropped | 等了 5 分鐘，或失敗了 3 輪 | 記一行日誌，刪掉 |

隊列放在內存裡，不進庫。停止前 `drain` 會先把隊列走完（3.12），重啟期間的消息 Telegram 也會重發，持久化不值這份複雜度。

`_Chat` 只剩這些：標題、是不是私聊、問題隊列、提問人最後說話的時間、worker 任務、一個待考慮的主動發言時刻。現在的 `trigger`、`reason`、`generating`、`committed`、`restarts`、`dirty` 全部去掉，狀態從六個標誌換成一個隊列。

### 3.3 每個群一個 worker

`handle` 只做兩件事：把問題放進隊列；沒有 worker 就起一個。worker 就是 3.1 的第 1–7 步組成的循環。同一個群同時最多一次調用在路上。

不取消，理由是：

- 取消扔掉的是一次已經付了錢的 6.6 萬 token 調用，而現在被限流正是因為調用太多。
- 現在最多也只取消重來一次，第二次還在想時再來的消息照樣得排隊。排隊這條路反正要做對，做對了就不需要取消。
- 人也會有消息交錯的時候：我剛回完，對方說“算了不用了”，很正常。

同一個群不併發兩輪：後一輪要看到前一輪我說了什麼，否則會重複回答或者自相矛盾。

### 3.4 給模型看什麼

`transcript.py` 不改。最近 30 條照舊渲染，所以語料和檢索出來的場面看起來還和現場聊天一樣。

只在聊天記錄本身說不清“還有誰在等我”時，在末尾加一條 system 消息。它用第一人稱寫，放在現在的重試提示所在的位置：

```
（冲我来的，还没回：
[1] 小林: 真红 今晚开黑吗
[2] 阿树（回复我「来」）: 几点
[3] 小林: 顺便问下那个报错怎么修）
```

每一行都用 `render_lines` 渲染，和聊天記錄裡的寫法一模一樣。清單裡帶著原話，所以那條消息就算已經滑出最近 30 條，模型也看得到。

什麼時候加清單：這一批不止一個問題，或者那個問題後面又有別人（包括我）說過話。只有一個問題、而且它後面只有提問人自己的話時不加，這時提示詞和現在逐字相同。`eval run` 走的就是這種情況，所以現有的風格數字仍然有效。日常回覆裡加不加清單各佔多少，第 1 步上線後日誌裡會有數。

另外兩處跟著改：

- `build_messages` 現在遇到“最後一條是我說的”就返回 None。改成有問題要回時照樣拼，只有主動發言時才保留這條規則。丟問題那個 bug 的根就在這裡。
- 檢索現在用聊天末尾 4 行作查詢，而且最後一條是我說的就不檢索。改成有問題時用這些問題的原話作查詢。

### 3.5 `say` 工具和對號

工具定義只有一份，每次調用都一樣。不按情況換工具，免得破壞緩存前綴。

```json
"say": {
  "description": "在聊天里说话。一条消息是数组里的一个元素；回清单里的某一句，就把它的编号写进 to。",
  "parameters": {"messages": {"type": "array", "items": {
      "type": "object",
      "properties": {"text": {"type": "string"}, "to": {"type": "integer"}},
      "required": ["text"]}}}
}
```

解析時放寬：元素是純字符串也收下，當作沒寫 `to`；`to` 寫了清單裡沒有的編號，也當沒寫。

對號的規則：

- 這一批只有一個問題時，所有行都算回它，不看 `to`。
- 不止一個時，按 `to` 分組，組的順序就是模型寫的順序。沒寫 `to` 的行是說給大家的。
- 至少被一行指到的問題算 answered，其餘 taken 的都算 passed。模型調了 `stay_silent` 就全部 passed。

一次調用答幾個人，而不是每個問題調一次。一是每次調用 6.6 萬 token，五個人問就是五倍。二是分開調的回答彼此看不見，會重複、會矛盾。人在群裡也是掃一眼，挨個回。

### 3.6 引用規則

| 情況 | 引用 |
|---|---|
| 私聊 | 從不 |
| 群裡，這一輪只回一個問題 | 從它算起別人又發了 4 條以上（發送時數）才引用，和現在一樣，但目標固定是這個問題，不會被後來的消息換掉 |
| 群裡，這一輪回了不止一個問題 | 每組第一條都引用它回的那條 |
| 沒寫 `to` 的行，以及每組的後續行 | 不引用 |

Telegram 的 `allow_sending_without_reply` 照舊打開，原消息被刪了也能發出去。

### 3.7 順序和公平

- 取批按先來後到，每輪最多 6 個問題、每人最多 3 個。超出的留在 open 裡排下一輪，不扔。一個人連著點十次，別人的問題照樣能進下一輪。
- 同一個人的幾個問題都進清單，模型可以一句回完，其餘的就是 passed。
- 發送順序按模型寫的順序。它看過整段聊天，排得比到達順序更自然。

### 3.8 長回覆、代碼和條數上限

- **不截斷**。每組最多 `max(1, min(max_burst, 12 // 組數))` 條，沒寫 `to` 的行也算一組。所以一組時最多 6 條，三組時每組 4 條，一輪總共不超過 12 條，留在 Telegram 每個群每分鐘 20 條的限制以內。超出的行用換行接到這組最後一條後面，不扔。
- **代碼發一整條**。模型用 ``` 包起來的內容算一整塊：保留換行，去掉圍欄，不做 `clean` 的逐行清理，用 Telegram 的 `pre` 實體發成一條等寬消息，打字停頓按封頂值算。超過 Telegram 4096 字的上限時按行切成幾條。現在 `clean` 會把它拆成一行一條，`_EMPHASIS` 還會刪掉反引號。
- **不為長度重試**。`too_long` 照樣檢查、照樣記進日誌，但不再整次重調：數據裡第二稿多數還是太長，最後照樣發了，只是多等了一倍時間。AI 腔的重試保留，因為它少見，而且一旦出現就出戲。
- 每輪最多調兩次模型，第二次只出現在三種情況：超時、空回覆、AI 腔。

### 3.9 延遲預算、超時和過期

| 項 | 值 | 理由 |
|---|---|---|
| 安靜窗口、最長等待 | 2.5 秒、8 秒（不變） | 消息來得越密，一批越大 |
| 第一次調用超時 | 40 秒 | 當天下午 p50 是 3.8 秒，p90 是 8.3 秒，40 秒只攔真正卡住的 |
| 超時後不帶思考重試 | 剩下的 20 秒 | 和現在一樣只重試一次，但整輪封頂 60 秒 |
| SDK 自帶的重試 | 關掉（只對聊天用的模型設 `max_retries=0`） | 現在 SDK 遇到 429 或超時會先自己重試一次，遇到 429 還會先按 `retry-after` 等，這段時間算在調用耗時裡，引擎看不到。91.7 秒那輪是不是這樣還沒確認，第 1 步先把每次嘗試的耗時記下來 |
| 問題過期 | 5 分鐘 | 過了 5 分鐘群裡早聊到別處了，提問的人可以再問 |

現在超時是 60 秒，加上 SDK 自己重試一次，一次調用最長能拖兩分鐘，再加上不帶思考的重試，一輪最長四分鐘以上。

### 3.10 被限流時

- 主模型失敗時，現在已經會切到備用模型 30 分鐘。補一條：備用也失敗、而這次還沒試過主模型時，再試一次主模型，因為額度是滾動的，主模型可能已經恢復了。被 429 拒掉的請求不花額度。
- 兩個都失敗時，這一輪的問題回到 open，worker 等一會兒再試：有 `retry-after` 就按它等（封頂 60 秒），沒有就先等 10 秒、再等 30 秒。網關的限流是全局的，所以“等到幾點”記在 harness 上，所有群一起等，而不是每個群各撞一次。
- 什麼也不說。人手機沒電時也是不回；等額度回來，排著的問題會帶著引用補上，像離開一會兒又回來的人。不發“等等”之類的固定話：那不是我說話的樣子，而且會多佔一條消息。
- 一個問題失敗滿 3 輪，或者等過了 5 分鐘，就算 dropped，記一行日誌。

### 3.11 主動發言

主動發言不算問題。worker 先回問題；沒有 open 的問題、也沒有調用在路上時，才考慮主動發言。規則和現在一樣：任何人說話都重新計時，門控 `Gate` 不變。

- 主動發言還在等的時候來了問題：放棄這次主動發言，直接回問題，反正那一輪看得到同樣的上下文。
- 主動發言的調用已經在路上：不取消，問題排進下一輪。

### 3.12 停止前

`drain` 現在等正在跑的任務，最多 60 秒。改成等 worker 把隊列走完，同樣最多 60 秒，而且停止時不再開始新的主動發言。到時還沒回的問題記日誌。

`answer()`（`eval run` 和終端裡的 `shinnku chat` 在用）保留原來的簽名：放進一個問題，直接跑一輪，返回 `Outcome`。

### 3.13 留給問題分類的接口

另一個會話在計劃識別“拿我測 AI 能力”的問題，打算不帶思考、短短地頂回去。接口這樣留，不依賴它最後選哪種方案：

- 問題進隊時可以掛一個判定，結果是 `profile`，說明回它的那次調用怎麼調（思考開不開、加哪條提示）。沒有判定，或者判定失敗，就是現在的普通回覆。判定可以是異步的，也可以調模型，進隊時就開始，不等防抖結束。
- 取批前等這批問題的判定結果，最多等多久由判定那邊定，等不到就按普通回覆。
- 一批裡只放同一種 `profile` 的問題，不同的排下一輪，因為思考是按調用開關的，一次調用裡沒法有的想、有的不想。不帶思考的那種先回，它快；同一種裡先來後到。
- 如果那邊的方案是讓模型在同一次調用裡自己判斷，就用不到這個接口，兩者也不衝突。

[v2-probe-plan.md](v2-probe-plan.md) 第 9 節的四點要求（進來就判、結果掛在消息上、回之前最多等 3 秒、考題單獨一次調用且先發）都落在這個接口裡。

這個字段等那邊的方案落地時再加，現在不放一個只有默認值的空接口。

| 16:28 前後兩個點名再也沒回 | 進了隊列；16:29:35 那輪發完後，下一輪帶著清單回它們，各自引用 |
| 91.7 秒那一輪，回的是另一個人，觸發者卻換成了最後點名的人 | 每個問題自己的消息定下就不變，回誰引用誰 |
| 兩段代碼都停在第 6 條 | 代碼整塊發成一條等寬消息 |
| 三輪各調兩次，最長 91.7 秒 | 不為長度重試，各調一次；單次調用 40 秒封頂 |
| 16:18–16:21 五次 429，一句不回 | 問題回到隊列，額度回來後補上（5 分鐘以內） |
| 有人對著代碼的某一行回覆新問題 | 代碼只有一條消息 |

## 5. 調用預算

- 每輪最多 2 次調用，第二次只在失敗或 AI 腔時出現。
- 同一個群同時只有一次調用在路上，所以一陣子裡的調用次數取決於持續多久，和來了幾個問題無關。按調用 4 秒、發送 5 秒、安靜窗口 2.5 秒算，問題來得再密，一個群大約每 10 秒一輪。來的問題越多，每輪的清單越長，調用次數不變。
- 不加每小時上限。以前加過每群每小時 60 次，群裡聊得多時 bot 整段不回話，後來刪了。

## 6. 測試

全部用 `tests/v2/fakes.py` 的 `FakeModel`（可以設延遲）和 `FakeOutbox`，內容都是編的。`FakeOutbox` 發出的消息 id 從 1000 起，比測試裡的問題大，和 Telegram 裡“我的回覆排在問題後面”一樣。

第一個測試先寫，而且在現有代碼上必須失敗：

```
小林點名 → 模型調用在路上
阿樹點名 → （現在：取消重來）
阿秋點名 → （現在：只標 dirty）
全部結束後：阿秋那條必須得到回覆
```

在現有代碼上，阿秋那條什麼回覆都沒有。這就是線上丟問題的那條路徑。

| 測試 | 斷言 |
|---|---|
| 多問題對號 | 模型回 `to=1`、`to=2` 兩組 → 兩組第一條分別引用對應的消息 |
| 引用目標固定 | 回答期間新來的點名，不會變成這次回答的引用目標 |
| 不取消 | 調用期間進來的消息不產生第二次併發調用，`finished == len(calls)` |
| 調用次數有上限 | 一次調用期間 10 個人各點名一次 → 後面再調兩次，清單分別是 6 個和 4 個 |
| 看了不回不循環 | 兩個問題只回了一個 → 另一個 passed，不再調用 |
| 追問 | 回答期間提問人補一句 → 下一輪清單裡有這句；補五句也只算一條追問 |
| 失敗回隊 | 第一次拋 429 → 問題回 open，退避後回答；超過過期時間 → dropped 並記日誌 |
| 備用失敗再試主模型 | 主模型在冷卻期，備用拋 429 → 用主模型回答 |
| 不截斷 | 一組比 `max_burst` 多 2 行 → 條數等於 `max_burst`，最後一條包含後 3 行 |
| 代碼整塊 | ``` 包著的 5 行 → 一條消息，換行保留，帶 `pre` 實體 |
| 單問題提示詞不變 | 只有一個問題、後面只有提問人的話 → 提示詞和 `test_prompt_shape` 一致 |
| 主動發言讓位 | 主動發言還在等時來了點名 → 不調主動發言，直接回問題 |
| `drain` | 隊列裡還有問題時調 `drain` → 回完才返回 |

過期時間、退避時間按 `quiet_window_s` 那樣做成設置項，測試裡設成幾十毫秒。

要改的現有測試：`test_new_line_while_thinking_restarts_once` 改成“不取消，補的話作為追問進下一輪”；`test_long_twice_is_sent_anyway` 改成“太長不重試”。

## 7. 遷移步驟

每一步單獨落地、帶著測試，測試過了就提交推送。每步上線只重啟一次，挑群裡安靜的時候。

| 步 | 內容 | 測試 | 上線後看什麼 |
|---|---|---|---|
| 1 問題隊列 | `Ask`、精簡後的 `_Chat`、worker 循環、追問；不取消；`build_messages` 有問題時不再因為最後是我說的而放棄；“還沒回的”清單；檢索用問題原話；單個問題的引用目標固定。`say` 先不改，多個問題時不引用 | 丟問題的復現、不取消、調用次數上限、看了不回不循環、追問、單問題提示詞不變、主動發言讓位、`drain` | 新日誌 `turn chat= asks= listed= answered= passed= open_left=` 和 `ask dropped why=`，以及每次嘗試的耗時。dropped 應該只有過期 |
| 2 對號和引用 | `say` 的 `to`；按組發；多個問題時每組第一條引用 | 多問題對號、引用目標固定 | 多問題的輪次裡有多少行帶了有效的 `to` |
| 3 發送 | 不截斷，超出的行合併，一輪最多 12 條；代碼整塊加 `pre`；去掉 `too_long` 重試；Telegram 的 `RetryAfter` 按它說的時間等 | 不截斷、代碼整塊、太長不重試 | 調兩次的輪次比例應該明顯下降 |
| 4 失敗處理 | 聊天模型 `max_retries=0`；一輪 40+20 秒封頂；失敗回隊、全局退避、5 分鐘過期；備用失敗再試主模型 | 失敗回隊、備用失敗再試主模型 | `respond failed` 應該消失，換成回隊和過期的計數 |
| 5 分類接口 | 等測 AI 問題的計劃定下來再做 | 跟那邊的測試一起寫 | — |

先做 1：丟問題是最傷的，而且後面幾步都建在隊列上。2 和 3 互不依賴，順序可以換。

## 11. 風險

- 模型不一定按編號填 `to`，或者會亂填。清單裡沒有的編號當沒寫，單個問題時也不看 `to`。第 2 步上線後看日誌。
- 一次答幾個人，回答可能變長，碰到每組上限時會合併成多行的消息，不像我平時一句一條。只在一陣子問題裡出現。
- 清單是新加的內容，出現時提示詞和評估過的不一樣。只在多個問題或有歧義時出現。
- 5 分鐘過期和失敗 3 輪丟棄之後，仍然會有問題得不到回答，但日誌裡有數。
- 去掉 `too_long` 重試後，長消息可能變多。上線前後對比 `too_long` 的比例。
