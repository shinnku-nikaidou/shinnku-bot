# shinnku-bot v2：一阵问题同时来时怎么接

写于 2026-11-14，接在 [v2-gaps-plan.md](v2-gaps-plan.md) 之后。只是计划，代码还没动。

它替换 `harness/engine.py` 里“一个群只有一个触发者”的那一套（防抖、取消重来、`dirty`），连带 `harness/send.py`、`harness/act.py` 的 `say` 工具和 `harness/hooks.py` 的条数截断。

## 1. 问题

2026-11-14 16:18–16:45（UTC）一个群里几个人轮流 @ 和回复 bot，连着出难题。下面的数字都来自服务日志，日志里只有条数、字数和耗时。

| 现象 | 原因 | 证据 |
|---|---|---|
| 有的问题再也没人回 | 回答期间进来的点名，只会让这一轮结束后“再看一次”（`dirty`）。可我的回复在 Telegram 里排在这些问题后面，再看时最后一条是我自己说的，`build_messages` 返回 None，什么也不做，也不留日志。就算问题进了提示词，模型也不知道还有谁在等，而“触发者”又被换成了最后来的那个人 | 16:28 前后两个人各点名一次，都没得到回复，其中一人 4 分钟后又问了一遍才得到回答。日志分不清这两条是被 `dirty` 那条路丢掉的，还是进了提示词、模型只回了别人。现在的设计两种都可能 |
| 引用不对，或者没有引用 | 引用目标是发送那一刻的 `chat.trigger`，它每来一条点名就被覆盖，可能指向这次回答根本没看到的消息。一轮只有第一条能引用，`say` 没法说哪句回谁，而且别人又发了 4 条以上才引用 | 几个人同时问时，回复混成一串，看不出在回谁 |

缓存命中率另有一个会话在修。本计划不碰缓存，但按“每次调用都很贵”来设计。

## 2. 结论一览

| 要决定的 | 决定 | 见 |
|---|---|---|
| 工作单位 | 按问题记账，按轮调用：每条冲我来的消息单独记一笔，模型一轮只调一次，一次看完所有还没回的 | 3.2、3.5 |
| 怎么记，保证不丢 | 每个群一个内存队列，问题有明确的状态；看过不回算处理完，失败的回到队列 | 3.2 |
| 生成和发送时进来的消息 | 不取消，排进下一轮 | 3.3 |
| 一次答几个人，怎么对上号 | 一次调用答整批；`say` 的每条带 `to`；只在说不清时，在末尾加一张“还没回的”清单；`transcript.py` 不动 | 3.4、3.5 |
| 引用 | 单个问题照旧（目标固定）；多个问题时每组第一条都引用 | 3.6 |
| 顺序和公平 | 先来后到，每轮最多 6 个、每人最多 3 个，超出的排下一轮 | 3.7 |
| 长回复和代码 | 不截断，超出的行合并；代码整块发一条；一轮最多 12 条；不为长度重试 | 3.8 |
| 延迟、超时、过期 | 一轮封顶 60 秒；SDK 不自己重试；问题 5 分钟过期 | 3.9 |
| 被限流 | 先换另一个模型，再全局退避，问题回到队列；不说固定的话 | 3.10 |
| 主动发言、停止前 | 问题优先；`drain` 等队列走完 | 3.11、3.12 |
| 问题分类的接口 | 问题可带 `profile`，按 `profile` 分批 | 3.13 |

几条原则：

- **一条都不丢**。没回的问题都有记录，最后只能是“回了”“看了不回”“过期”三种结局之一，后两种也记日志。
- **调用开始了就不取消**。取消扔掉的是已经付过钱的调用。
- **看过不回也算处理了**。模型看到了某个问题、选择不回，就跟现在的 `stay_silent` 一样，不再追。这样不会因为一条刷屏而一直循环调用。
- **调用次数随时间增长，不随问题数增长**。一阵子里来十个问题和来两个问题，调用次数差不多。

## 3. 架构

### 3.1 流程

```
收到消息    存库（和现在一样）
  冲我来的？    是（私聊、回复我、@我、叫名字）→ 记成一个问题，状态 open
              否，发消息的人有 open 的问题 → 他还在打字，延长安静窗口
              否，发消息的人的问题正在回答 → 记成他的追问（每人最多一条，新的替换旧的）
              否 → 只存（话痨程度大于 0 时交给主动发言）

每个群一个 worker，有 open 的问题就转起来：
  1. 等      提问的人都安静 2.5 秒，或最早的 open 问题已经等了 8 秒
  2. 取批    open 问题按先来后到取，每轮最多 6 个、每人最多 3 个 → taken
  3. 拼提示词  最近 30 条照旧，需要时在末尾加“还没回的”清单
  4. 调模型   一次，不取消
  5. 发      按问题分组，每组第一条按规则引用它回的那条
  6. 收账    回到的 answered，看了没回的 passed；失败的回到 open，稍后重来；过期的 dropped
  7. 还有 open 的就回到 1；没有就看主动发言；再没有，worker 退出
```

“什么算冲我来”（`attention.py`）不变，只多了一条：回答期间提问人自己补的话算追问。现在这种情况是取消重来一次，同样多花一次调用，但白扔一次；改成追问后，下一轮模型看得到我的回答和他补的话，没必要回就不回。

### 3.2 问题和它的状态

```python
@dataclass
class Ask:
    msg: Msg          # 冲我来的那条，进队时定下，之后不变
    reason: str       # private / reply / mention / name / followup
    arrived: float    # 进队时间
    state: str        # 见下表
    tries: int = 0    # 失败过几轮
```

| 状态 | 意思 | 去向 |
|---|---|---|
| open | 等着进下一轮 | 进批 → taken；过期 → dropped |
| taken | 在这一轮的提示词里 | 回到了 → answered；看了没回 → passed；这一轮失败 → open（tries 加 1） |
| answered、passed | 处理完了，从队列里删掉 | — |
| dropped | 等了 5 分钟，或失败了 3 轮 | 记一行日志，删掉 |

队列放在内存里，不进库。停止前 `drain` 会先把队列走完（3.12），重启期间的消息 Telegram 也会重发，持久化不值这份复杂度。

`_Chat` 只剩这些：标题、是不是私聊、问题队列、提问人最后说话的时间、worker 任务、一个待考虑的主动发言时刻。现在的 `trigger`、`reason`、`generating`、`committed`、`restarts`、`dirty` 全部去掉，状态从六个标志换成一个队列。

### 3.3 每个群一个 worker

`handle` 只做两件事：把问题放进队列；没有 worker 就起一个。worker 就是 3.1 的第 1–7 步组成的循环。同一个群同时最多一次调用在路上。

不取消，理由是：

- 取消扔掉的是一次已经付了钱的 6.6 万 token 调用，而现在被限流正是因为调用太多。
- 现在最多也只取消重来一次，第二次还在想时再来的消息照样得排队。排队这条路反正要做对，做对了就不需要取消。
- 人也会有消息交错的时候：我刚回完，对方说“算了不用了”，很正常。

同一个群不并发两轮：后一轮要看到前一轮我说了什么，否则会重复回答或者自相矛盾。

### 3.4 给模型看什么

`transcript.py` 不改。最近 30 条照旧渲染，所以语料和检索出来的场面看起来还和现场聊天一样。

只在聊天记录本身说不清“还有谁在等我”时，在末尾加一条 system 消息。它用第一人称写，放在现在的重试提示所在的位置：

```
（冲我来的，还没回：
[1] 小林: 真红 今晚开黑吗
[2] 阿树（回复我「来」）: 几点
[3] 小林: 顺便问下那个报错怎么修）
```

每一行都用 `render_lines` 渲染，和聊天记录里的写法一模一样。清单里带着原话，所以那条消息就算已经滑出最近 30 条，模型也看得到。

什么时候加清单：这一批不止一个问题，或者那个问题后面又有别人（包括我）说过话。只有一个问题、而且它后面只有提问人自己的话时不加，这时提示词和现在逐字相同。`eval run` 走的就是这种情况，所以现有的风格数字仍然有效。日常回复里加不加清单各占多少，第 1 步上线后日志里会有数。

另外两处跟着改：

- `build_messages` 现在遇到“最后一条是我说的”就返回 None。改成有问题要回时照样拼，只有主动发言时才保留这条规则。丢问题那个 bug 的根就在这里。
- 检索现在用聊天末尾 4 行作查询，而且最后一条是我说的就不检索。改成有问题时用这些问题的原话作查询。

### 3.5 `say` 工具和对号

工具定义只有一份，每次调用都一样。不按情况换工具，免得破坏缓存前缀。

```json
"say": {
  "description": "在聊天里说话。一条消息是数组里的一个元素；回清单里的某一句，就把它的编号写进 to。",
  "parameters": {"messages": {"type": "array", "items": {
      "type": "object",
      "properties": {"text": {"type": "string"}, "to": {"type": "integer"}},
      "required": ["text"]}}}
}
```

解析时放宽：元素是纯字符串也收下，当作没写 `to`；`to` 写了清单里没有的编号，也当没写。

对号的规则：

- 这一批只有一个问题时，所有行都算回它，不看 `to`。
- 不止一个时，按 `to` 分组，组的顺序就是模型写的顺序。没写 `to` 的行是说给大家的。
- 至少被一行指到的问题算 answered，其余 taken 的都算 passed。模型调了 `stay_silent` 就全部 passed。

一次调用答几个人，而不是每个问题调一次。一是每次调用 6.6 万 token，五个人问就是五倍。二是分开调的回答彼此看不见，会重复、会矛盾。人在群里也是扫一眼，挨个回。

### 3.6 引用规则

| 情况 | 引用 |
|---|---|
| 私聊 | 从不 |
| 群里，这一轮只回一个问题 | 从它算起别人又发了 4 条以上（发送时数）才引用，和现在一样，但目标固定是这个问题，不会被后来的消息换掉 |
| 群里，这一轮回了不止一个问题 | 每组第一条都引用它回的那条 |
| 没写 `to` 的行，以及每组的后续行 | 不引用 |

Telegram 的 `allow_sending_without_reply` 照旧打开，原消息被删了也能发出去。

### 3.7 顺序和公平

- 取批按先来后到，每轮最多 6 个问题、每人最多 3 个。超出的留在 open 里排下一轮，不扔。一个人连着点十次，别人的问题照样能进下一轮。
- 同一个人的几个问题都进清单，模型可以一句回完，其余的就是 passed。
- 发送顺序按模型写的顺序。它看过整段聊天，排得比到达顺序更自然。

### 3.8 长回复、代码和条数上限

- **不截断**。每组最多 `max(1, min(max_burst, 12 // 组数))` 条，没写 `to` 的行也算一组。所以一组时最多 6 条，三组时每组 4 条，一轮总共不超过 12 条，留在 Telegram 每个群每分钟 20 条的限制以内。超出的行用换行接到这组最后一条后面，不扔。
- **代码发一整条**。模型用 ``` 包起来的内容算一整块：保留换行，去掉围栏，不做 `clean` 的逐行清理，用 Telegram 的 `pre` 实体发成一条等宽消息，打字停顿按封顶值算。超过 Telegram 4096 字的上限时按行切成几条。现在 `clean` 会把它拆成一行一条，`_EMPHASIS` 还会删掉反引号。
- **不为长度重试**。`too_long` 照样检查、照样记进日志，但不再整次重调：数据里第二稿多数还是太长，最后照样发了，只是多等了一倍时间。AI 腔的重试保留，因为它少见，而且一旦出现就出戏。
- 每轮最多调两次模型，第二次只出现在三种情况：超时、空回复、AI 腔。

### 3.9 延迟预算、超时和过期

| 项 | 值 | 理由 |
|---|---|---|
| 安静窗口、最长等待 | 2.5 秒、8 秒（不变） | 消息来得越密，一批越大 |
| 第一次调用超时 | 40 秒 | 当天下午 p50 是 3.8 秒，p90 是 8.3 秒，40 秒只拦真正卡住的 |
| 超时后不带思考重试 | 剩下的 20 秒 | 和现在一样只重试一次，但整轮封顶 60 秒 |
| SDK 自带的重试 | 关掉（只对聊天用的模型设 `max_retries=0`） | 现在 SDK 遇到 429 或超时会先自己重试一次，遇到 429 还会先按 `retry-after` 等，这段时间算在调用耗时里，引擎看不到。91.7 秒那轮是不是这样还没确认，第 1 步先把每次尝试的耗时记下来 |
| 问题过期 | 5 分钟 | 过了 5 分钟群里早聊到别处了，提问的人可以再问 |

现在超时是 60 秒，加上 SDK 自己重试一次，一次调用最长能拖两分钟，再加上不带思考的重试，一轮最长四分钟以上。

### 3.10 被限流时

- 主模型失败时，现在已经会切到备用模型 30 分钟。补一条：备用也失败、而这次还没试过主模型时，再试一次主模型，因为额度是滚动的，主模型可能已经恢复了。被 429 拒掉的请求不花额度。
- 两个都失败时，这一轮的问题回到 open，worker 等一会儿再试：有 `retry-after` 就按它等（封顶 60 秒），没有就先等 10 秒、再等 30 秒。网关的限流是全局的，所以“等到几点”记在 harness 上，所有群一起等，而不是每个群各撞一次。
- 什么也不说。人手机没电时也是不回；等额度回来，排着的问题会带着引用补上，像离开一会儿又回来的人。不发“等等”之类的固定话：那不是我说话的样子，而且会多占一条消息。
- 一个问题失败满 3 轮，或者等过了 5 分钟，就算 dropped，记一行日志。

### 3.11 主动发言

主动发言不算问题。worker 先回问题；没有 open 的问题、也没有调用在路上时，才考虑主动发言。规则和现在一样：任何人说话都重新计时，门控 `Gate` 不变。

- 主动发言还在等的时候来了问题：放弃这次主动发言，直接回问题，反正那一轮看得到同样的上下文。
- 主动发言的调用已经在路上：不取消，问题排进下一轮。

### 3.12 停止前

`drain` 现在等正在跑的任务，最多 60 秒。改成等 worker 把队列走完，同样最多 60 秒，而且停止时不再开始新的主动发言。到时还没回的问题记日志。

`answer()`（`eval run` 和终端里的 `shinnku chat` 在用）保留原来的签名：放进一个问题，直接跑一轮，返回 `Outcome`。

### 3.13 留给问题分类的接口

另一个会话在计划识别“拿我测 AI 能力”的问题，打算不带思考、短短地顶回去。接口这样留，不依赖它最后选哪种方案：

- 问题进队时可以挂一个判定，结果是 `profile`，说明回它的那次调用怎么调（思考开不开、加哪条提示）。没有判定，或者判定失败，就是现在的普通回复。判定可以是异步的，也可以调模型，进队时就开始，不等防抖结束。
- 取批前等这批问题的判定结果，最多等多久由判定那边定，等不到就按普通回复。
- 一批里只放同一种 `profile` 的问题，不同的排下一轮，因为思考是按调用开关的，一次调用里没法有的想、有的不想。不带思考的那种先回，它快；同一种里先来后到。
- 如果那边的方案是让模型在同一次调用里自己判断，就用不到这个接口，两者也不冲突。

[v2-probe-plan.md](v2-probe-plan.md) 第 9 节的四点要求（进来就判、结果挂在消息上、回之前最多等 3 秒、考题单独一次调用且先发）都落在这个接口里。

这个字段等那边的方案落地时再加，现在不放一个只有默认值的空接口。

| 有人对着代码的某一行回复新问题 | 代码只有一条消息 |

## 5. 调用预算

- 每轮最多 2 次调用，第二次只在失败或 AI 腔时出现。
- 同一个群同时只有一次调用在路上，所以一阵子里的调用次数取决于持续多久，和来了几个问题无关。按调用 4 秒、发送 5 秒、安静窗口 2.5 秒算，问题来得再密，一个群大约每 10 秒一轮。来的问题越多，每轮的清单越长，调用次数不变。
- 不加每小时上限。以前加过每群每小时 60 次，群里聊得多时 bot 整段不回话，后来删了。

## 6. 测试

全部用 `tests/v2/fakes.py` 的 `FakeModel`（可以设延迟）和 `FakeOutbox`，内容都是编的。`FakeOutbox` 发出的消息 id 从 1000 起，比测试里的问题大，和 Telegram 里“我的回复排在问题后面”一样。

第一个测试先写，而且在现有代码上必须失败：

```
小林点名 → 模型调用在路上
阿树点名 → （现在：取消重来）
阿秋点名 → （现在：只标 dirty）
全部结束后：阿秋那条必须得到回复
```

在现有代码上，阿秋那条什么回复都没有。这就是线上丢问题的那条路径。

| 测试 | 断言 |
|---|---|
| 多问题对号 | 模型回 `to=1`、`to=2` 两组 → 两组第一条分别引用对应的消息 |
| 引用目标固定 | 回答期间新来的点名，不会变成这次回答的引用目标 |
| 不取消 | 调用期间进来的消息不产生第二次并发调用，`finished == len(calls)` |
| 调用次数有上限 | 一次调用期间 10 个人各点名一次 → 后面再调两次，清单分别是 6 个和 4 个 |
| 看了不回不循环 | 两个问题只回了一个 → 另一个 passed，不再调用 |
| 追问 | 回答期间提问人补一句 → 下一轮清单里有这句；补五句也只算一条追问 |
| 失败回队 | 第一次抛 429 → 问题回 open，退避后回答；超过过期时间 → dropped 并记日志 |
| 备用失败再试主模型 | 主模型在冷却期，备用抛 429 → 用主模型回答 |
| 不截断 | 一组比 `max_burst` 多 2 行 → 条数等于 `max_burst`，最后一条包含后 3 行 |
| 代码整块 | ``` 包着的 5 行 → 一条消息，换行保留，带 `pre` 实体 |
| 单问题提示词不变 | 只有一个问题、后面只有提问人的话 → 提示词和 `test_prompt_shape` 一致 |
| 主动发言让位 | 主动发言还在等时来了点名 → 不调主动发言，直接回问题 |
| `drain` | 队列里还有问题时调 `drain` → 回完才返回 |

过期时间、退避时间按 `quiet_window_s` 那样做成设置项，测试里设成几十毫秒。

要改的现有测试：`test_new_line_while_thinking_restarts_once` 改成“不取消，补的话作为追问进下一轮”；`test_long_twice_is_sent_anyway` 改成“太长不重试”。

## 7. 迁移步骤

每一步单独落地、带着测试，测试过了就提交推送。每步上线只重启一次，挑群里安静的时候。

| 步 | 内容 | 测试 | 上线后看什么 |
|---|---|---|---|
| 1 问题队列 | `Ask`、精简后的 `_Chat`、worker 循环、追问；不取消；`build_messages` 有问题时不再因为最后是我说的而放弃；“还没回的”清单；检索用问题原话；单个问题的引用目标固定。`say` 先不改，多个问题时不引用 | 丢问题的复现、不取消、调用次数上限、看了不回不循环、追问、单问题提示词不变、主动发言让位、`drain` | 新日志 `turn chat= asks= listed= answered= passed= open_left=` 和 `ask dropped why=`，以及每次尝试的耗时。dropped 应该只有过期 |
| 2 对号和引用 | `say` 的 `to`；按组发；多个问题时每组第一条引用 | 多问题对号、引用目标固定 | 多问题的轮次里有多少行带了有效的 `to` |
| 3 发送 | 不截断，超出的行合并，一轮最多 12 条；代码整块加 `pre`；去掉 `too_long` 重试；Telegram 的 `RetryAfter` 按它说的时间等 | 不截断、代码整块、太长不重试 | 调两次的轮次比例应该明显下降 |
| 4 失败处理 | 聊天模型 `max_retries=0`；一轮 40+20 秒封顶；失败回队、全局退避、5 分钟过期；备用失败再试主模型 | 失败回队、备用失败再试主模型 | `respond failed` 应该消失，换成回队和过期的计数 |
| 5 分类接口 | 等测 AI 问题的计划定下来再做 | 跟那边的测试一起写 | — |

先做 1：丢问题是最伤的，而且后面几步都建在队列上。2 和 3 互不依赖，顺序可以换。

## 11. 风险

- 模型不一定按编号填 `to`，或者会乱填。清单里没有的编号当没写，单个问题时也不看 `to`。第 2 步上线后看日志。
- 一次答几个人，回答可能变长，碰到每组上限时会合并成多行的消息，不像我平时一句一条。只在一阵子问题里出现。
- 清单是新加的内容，出现时提示词和评估过的不一样。只在多个问题或有歧义时出现。
- 5 分钟过期和失败 3 轮丢弃之后，仍然会有问题得不到回答，但日志里有数。
- 去掉 `too_long` 重试后，长消息可能变多。上线前后对比 `too_long` 的比例。
