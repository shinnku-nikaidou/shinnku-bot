寫計劃之後有三處變化：

- **不建測試 bot**。按你的要求直接用正式 bot 在你自己的群裡測，測試時先停舊服務。
- **隱私規則放寬**。Claude 可以自己在真實數據上運行只輸出結構和統計的命令；仍然不主動讀內容。
- **依賴提前精簡**。你要求升到最新依賴，而全量升級會連帶下載幾個 G 的 torch 和 CUDA 庫。所以 `pyproject.toml` 現在只列新 bot 用到的包（都是最新版），同步時用 `uv sync --inexact`，舊 bot 用的包留在虛擬環境裡不刪。切換前不要跑不帶 `--inexact` 的 `uv sync`，否則舊 bot 重啟會失敗。

### 目前的評估結論（2026-11-12）

真實數據規模（兩個群都導完後）：共 108 萬條消息，你的發言 22.9 萬條，回覆對 80,588 個，每個群留出最新的 300 個作測試集。下面三項實驗是在第二個群導到一半時跑的，當時回覆對約 7 萬個。

| 實驗 | 結果 | 說明 |
|---|---|---|
| 僅佔位人設，100 個留出場面 | 99 個開口；單條長度中位數 bot 9 字、真人 11 字；連發 bot 1.84 條、真人 1.56 條；出戲率 20.8%；延遲中位數 2.0 秒 | 不帶任何真實樣本的起點 |
| 同一批回覆換裁判 | glm-5.3 低推理 48.5%，高推理 46.5%；kimi-k3 57.8%（只判出 45 條）；deepseek-v4-pro 29.3% | 裁判之間差得太多，而且有的明顯偏向 bot |
| 離線檢索驗證，100 個場面 | 檢索到的場面裡“我說過的話”與真實回覆的最高相似度 0.544，隨機場面 0.504；72% 的場面檢索勝過隨機；檢索耗時中位數 103 毫秒 | 檢索有效，幅度不大 |

由此改了兩點：

- **模型裁判不當主指標**。它在這裡不可靠，默認關閉（`--judge` 才開）。主指標改為“bot 回覆與真實回覆的語義接近度”、長度和連發分佈、出戲率，以及你本人做的 `eval quiz`。
- **評估默認小樣本**。默認 40 條、併發 4。原因見下。

還沒驗證的：加上固定樣本塊和檢索之後，比僅佔位人設好多少。這組對比因為額度用盡沒跑成。

### 提示詞大小：定在約 5 萬 token

2026-11-12 實測了大提示詞（內容是真實對話片段，價格為標價，額度實扣其 60%）：

| 提示詞 | 緩存沒命中 | 緩存命中 |
|---|---|---|
| 1.2 萬 token（107 個場面） | 約 4 秒 | 1.5 秒 |
| 5.0 萬 token（520 個場面） | 2.8 秒，約 $0.0075 | 未單獨測 |
| 9.8 萬 token（1,100 個場面） | 3.4 秒，$0.0147 | 2.6 秒，$0.0003 |
| 36.5 萬 token（3,900 個場面） | 6.6–8.2 秒，約 $0.04–0.055 | 3.5 秒，$0.0011 |

緩存在第一次請求之後要過 20–60 秒才生效，所以冷啟動後一分鐘內的回覆都是全價。

你定的大小是 5 萬 token 左右，對應 520 個固定樣本（`ANCHOR_SCENES=520`，現為默認值）。實際量到的提示詞是 50,124 token。樣本放大後效果是否更好沒有做對比評估，這是你決定不跑的。

### 網關額度

`opencode-go/*` 的模型共用一個滾動額度。2026-11-12 凌晨比較裁判時，並行跑了三輪高推理強度的重判，把額度用盡了，約半小時內所有請求返回 429。以後批量評估要先估規模，真機測試前不要把額度花在評估上。

## 1. 目標

把 5 年前寫的 Telegram bot 從零重寫，讓它的說話方式和開口時機都像 shinnku 本人。

判斷標準是盲測：給同一段上文，一句是本人當年真實說的，一句是 bot 生成的，裁判模型和本人都分不出來（準確率接近 50%）。

| 決定 | 說明 |
|---|---|

全部用合成的群聊內容測的，沒有用到真實聊天記錄。

## 4. 隱私規則

私密範圍：`~/tg-export/`、Telegram 登錄數據目錄、倉庫裡的 `data/` 和 `logs/`。

- Claude 不讀這些目錄。`.claude/settings.local.json` 的拒絕規則從現有兩條擴到 `data/**` 和 `logs/**`。
- 開發和測試只用合成數據：`tests/fixtures/` 裡按真實結構造的假導出和假人設。
- 真實數據上的命令由你來運行。
- 命令行只打印計數、分佈、耗時。含內容的結果寫到 `data/reports/`，給你自己看。
- 出錯時只打印異常類型和代碼位置。異常消息可能帶原文，所以寫到 `data/reports/last_error.txt`。
- 運行日誌默認不含消息文本，只記事件、id、長度、耗時和決策。含內容的追蹤另寫到 `data/trace/`。
- 蒸餾和評估會把聊天內容發到你的網關及其上游模型商。

## 5. 架構

### 5.1 一條消息的在線處理流程

```
1. 存庫      所有類型的消息都記下來（圖片、貼紙記成佔位符）
2. 感知      按群防抖，把對方的連發聚成一段再處理
3. 注意力    被 @、被回覆、私聊、被叫名字：直接通過
             其他情況：先過規則，後期再加分類器
4. 回憶      檢索“類似場面裡我說過的話”，取相關的人物卡和場景手冊
5. 拼提示詞  見 5.2
6. 模型調用  一次，必須調用一個工具
7. 發送前檢查  不通過就帶著對應規則重試一次，再不通過就沉默
8. 發送      分條發，帶打字狀態和按長度計算的延遲
9. 事後      後臺決定要不要記筆記，不阻塞回覆
```

生成期間如果被點名的那個人又發了新消息，取消並重來，最多重來一次。

### 5.2 提示詞的拼法

按“越穩定越靠前”排列，前三項能命中緩存。

1. 身份內核 `SELF.md`：第一人稱，用本人的口吻寫。
2. 固定樣本塊 `anchor.txt`：幾百段本人的真實對話，約 10–15k token。
3. 工具定義。
4. 這個群的群卡片，以及最近發言的人的人物卡。
5. 檢索到的 20–40 個類似場面，以“我記得的事”的形式給出，不寫成“請模仿以下示例”。
6. 群裡最近約 30 條消息：別人的話放在 user 位，格式是 `名字: 內容`；我說過的話放在 assistant 位，不加前綴。

兩條原則：

- 全程第一人稱，把要求寫成自我認知（“我說話很短”），不寫成命令（“你必須簡短”）。
- 風格主要靠第 2、5、6 項的真實樣本傳達。實測裡把風格寫成規則條文，會讓推理變成“我在執行某種風格”。

### 5.3 工具

| 工具 | 作用 | 何時提供 |
|---|---|---|
| `say(messages)` | 發 1–4 條短消息 | 始終 |
| `stay_silent()` | 這次不說話 | 始終 |
| `recall(query)` | 再搜一次自己的歷史，結果返回後再想一輪 | 始終，最多追加一輪 |
| `sticker(emoji)` | 從本人常用貼紙裡按 emoji 選一張 | 階段 7 |
| `remember(about, note)` | 記一條筆記 | 只在回覆後的後臺調用裡 |

### 5.4 發送前檢查

全部是確定性的代碼，不調模型。

- 去掉 markdown 標記；句末標點按風格指紋處理。
- 單條長度和連發條數按風格指紋的 95 分位封頂。
- AI 腔正則（“作為一個 AI”“希望對你有幫助”“首先……其次”之類）。
- 涉及錢、現實承諾、隱私的話題：不發，並私信你。

### 5.5 記憶文件

都在 `data/persona/` 下，bot 運行時讀取，部分可寫。

| 文件 | 內容 | 誰寫 |
|---|---|---|
| `SELF.md` | 我是誰、觀點、喜好 | 蒸餾生成，你可以手改 |
| `fingerprint.json` | 風格指紋（統計量） | 語料管線 |
| `anchor.txt` | 固定樣本塊 | 語料管線 |
| `people/<user_id>.md` | 我對這個人的印象、怎麼跟他說話 | 蒸餾生成，每晚更新 |
| `groups/<chat_id>.md` | 這個群是什麼地方、常聊什麼 | 蒸餾生成，每晚更新 |
| `skills/*.md` | 場景手冊：某類場面下我通常怎麼反應 | 蒸餾生成 |
| `diary/YYYY-MM-DD.md` | 第一人稱日記 | 每晚定時任務 |
| `notes.jsonl` | `remember` 記下的零散筆記 | bot，每晚併入人物卡 |

### 5.6 離線語料管線

入口是一個命令行工具 `shinnku`。

| 命令 | 做什麼 | 控制台打印 |
|---|---|---|
| `corpus probe` | 只看導出文件的結構 | 鍵名、類型、枚舉值、計數 |
| `corpus ingest` | 流式解析 `result.json`，寫入 `data/corpus.sqlite` | 消息數、各類型數、時間範圍 |
| `corpus pairs` | 切會話、合併連發、生成“上文 → 我的回覆”對，過濾命令、轉發、純鏈接、bot 消息 | 會話數、回覆對數、我的發言佔比 |
| `corpus holdout` | 按時間留出最近的一批回覆對作測試集，其餘才進入後續步驟 | 兩邊的數量 |
| `corpus stats` | 算風格指紋：句長、連發條數、標點、相對群友更常用的詞、emoji 和貼紙、語言混用、活躍時段 | 只有數值 |
| `corpus index` | 建 FTS5 trigram 索引和向量索引 | 條數、耗時 |
| `corpus anchor` | 按時間分層抽樣（近期權重高）選出固定樣本塊 | 條數、token 估計 |
| `corpus distill` | 用模型分塊提取再合併，生成 `SELF.md`、人物卡、群卡片、場景手冊；按採樣做，可斷點續跑 | 進度、token 用量 |

向量索引用 fastembed 在 CPU 上算，向量存成 numpy 內存映射文件，直接算點積，不引入向量數據庫。模型默認選一箇中文小模型，最後由評估決定。

### 5.7 評估

| 指標 | 怎麼算 | 目標 |
|---|---|---|
| 盲測準確率 | 裁判模型看上文和兩句回覆，猜哪句是真人 | 接近 50% |
| 本人盲測 | `eval quiz` 出一份小測驗，你來猜 | 接近 50% |
| 風格距離 | bot 回覆和真實回覆在句長、連發條數、標點率、字符 n-gram 上的分佈差 | 越小越好 |
| 出戲率 | 推理或正文裡出現“作為某某”“扮演”“用戶”等字樣的比例 | 接近 0 |
| 開口一致性 | 在抽樣時刻上，“bot 想開口”和“本人當時開口了”的精確率和召回率 | 階段 6 調 |
| 延遲和成本 | p50、p95、token、緩存命中率 | 記錄 |

每個指標都支持按開關做對照：有無檢索、有無固定樣本塊、推理開或關、換模型。裁判默認用另一家的模型，避免模型偏愛自己的輸出。

## 8. 分階段實施

階段 1 到 4 的代碼都能在合成數據上寫完並測試，不用等導出結束。

### 階段 0：導出（進行中，由你完成）

把兩個群導出成 JSON 到 `~/tg-export/`，不含媒體。

### 階段 1：骨架

- 新包 `src/shinnku_bot/`、配置、模型調用、運行時消息庫。
- 最小 harness：只在被點名時回覆；工具只有 `say` 和 `stay_silent`；帶發送前檢查和分條發送。
- 人設先用合成的佔位版本。
- 命令：`/start`、`/rua`、`/okiru`、`/quiet`、`/talk`、`/status`。

驗證：單元測試用假模型和假 Telegram 消息跑通；用測試 bot 在一個測試群裡 @ 它，得到分條的短回覆。

### 階段 2：語料管線

- 假導出生成器，結構和 Telegram Desktop 的 `result.json` 一致。
- `probe`、`ingest`、`pairs`、`holdout`、`stats`。

驗證：在假導出上各步的計數和預期一致。然後你在真實導出上跑 `probe`，把結構輸出給我核對解析器，再跑其餘幾步。

### 階段 3：檢索和提示詞

- `index`、`anchor`、混合檢索、5.2 的提示詞拼裝。

驗證：假數據上檢索能召回預設的相似場面；同一前綴連續兩次請求能命中緩存。

### 階段 4：評估和基線

- `eval gen`、裁判、各項指標、`eval quiz`。
- 跑出第一組基線數字，並做對照：有無檢索、有無固定樣本塊、推理開或關。

驗證：你在真實數據上跑，得到一張指標表。之後每個改動都看這張表。

### 階段 5：蒸餾和記憶

- `distill` 生成 `SELF.md`、人物卡、群卡片、場景手冊。
- `remember` 工具、每晚的日記和人物卡更新。

驗證：加入蒸餾產物後盲測準確率不變差；日記任務在假數據上能跑完。

### 階段 6：主動發言

- 規則版注意力：冷卻時間、接話窗口、每群的話癆程度、每小時調用上限。
- 分類器版：正例是本人開口的時刻，反例是本人當時在場但沒說話的時刻。
- 敏感話題轉給你。

驗證：開口一致性指標；先在測試群裡觀察一天再放到正式群。

貼紙、看圖，以及換一臺有顯卡的機器做 LoRA 微調並用同一套盲測對比。

## 10. 上線切換

1. 測試 bot 在測試群裡穩定運行，盲測指標達到你滿意的程度。
2. 停掉 `shinnku-bot.service`。
3. 把服務的 `ExecStart` 改成新入口，刪除第 9 節列的舊文件和舊依賴。
4. 在 BotFather 裡關閉正式 bot 的群隱私模式。
5. 啟動服務，先把話癆程度調到最低，觀察後再調高。

回退辦法：`ExecStart` 改回去，切回 `main` 分支。

## 11. 需要你做的事

1. 完成兩個群的導出。導出完後關掉為導出臨時開的遠程入口。
2. 在 BotFather 建一個測試 bot，token 填到 `TG_TOKEN_DEV`。正式 token 被舊 bot 佔著，兩個進程不能同時用。
3. 把測試 bot 的群隱私模式關掉（`/setprivacy` 選 Disable），否則它只能看到命令、@ 和回覆。
4. 告訴我 bot 要待在哪些群。把 bot 拉進群後發 `/status` 能看到群 id。
5. 在真實數據上運行語料和評估命令。

## 13. 風險

- 新登錄的設備導出可能被 Telegram 要求等 24 小時。
- Bot API 的 bot 看不到其他 bot 的消息；群隱私模式不關就看不到普通消息。
- 你的發言佔比還不知道，它決定可用的回覆對有多少。
- 1–2 個字的消息全文檢索匹配不到，只能靠向量檢索和上文。
- 模型可能該沉默時不沉默，或者反過來。評估裡單獨測這一點。
- 網關有額度和限速，全量蒸餾 200 萬條不現實，所以按採樣做並支持續跑。
